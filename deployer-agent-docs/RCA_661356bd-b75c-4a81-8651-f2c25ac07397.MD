# RCA — 502 on POST /api/paxity/payin (shoppingenchine.com)

## Summary
The production `POST /api/paxity/payin` route fails because the **production value of the `PAXITY_V2_API_KEY` secret is STALE / INVALID** — it does NOT match the new key `pax_live_OsYI4r5imHfMAQ8oZ6YpP6XoBdnGXY2A`. Paxity's live API rejects every create-transaction call with **401 Invalid API key ("unknown, revoked or inactive")**, and the backend route turns that upstream 401 into a 502 to the client.

The application code is fine (same code works in preview). This is a secret-value problem the user must fix in the Deployment Panel → Secrets, then redeploy.

## Evidence
### 1. Paxity rejects the production key with 401 (backend logs, run 661356bd)
```
paxity_router - ERROR - [Paxity] Création refusée (401) order=tmp_9cb1d842aa method=WAVE
  resp={'title': 'Invalid API key', 'status': 401,
        'detail': 'The provided API key is unknown, revoked or inactive',
        'instance': '/v2/external/transactions', 'request_id': 'sec_3cf5fbaad537'}
httpx - INFO - HTTP Request: POST https://api-v2.paxity.io/v2/external/transactions "HTTP/1.1 401 Unauthorized"
INFO:     136.68.30.50:0 - "POST /api/paxity/payin HTTP/1.1" 502 Bad Gateway
```
Every POST to Paxity (WAVE and ORANGE_MONEY) and every status-poll GET returns `401 Unauthorized`. The 502 the user sees is the route's response after the upstream 401.

### 2. The stored secret value is NOT the new key (list_secrets, active run)
```
PAXITY_V2_API_KEY  -> is_empty=false, matches_expected=false
```
`matches_expected=false` was checked against `pax_live_OsYI4r5imHfMAQ8oZ6YpP6XoBdnGXY2A`. So production still holds a different (old / revoked) key — consistent with the old key `pax_live_iGCV57WFaQbBuSgOi5Rh4TEr8hob2UJa` never having been replaced in production. (Secret values are never revealed; this is a value-match check.) `PAXITY_V2_ORG_ID` is present and non-empty.

### 3. Why /api/paxity/config returns 200 but /api/paxity/payin 502s
`/config` only reports that a key is present (`configured:true`) and the env label (`live`); it does not call Paxity, so it cannot detect an invalid key. `/payin` actually calls `POST /v2/external/transactions`, receives 401, and returns 502.

## Items explicitly ruled out
- **Pod crash / OOM:** No. `get_pod_events` shows both replicas `Running`, `ready=true`, `restart_count=0`, no OOMKilled, no CrashLoop. (One benign `Startup probe failed 503` at boot only, before readiness.) The worker does NOT die on the POST.
- **Egress to api-v2.paxity.io blocked:** No. The pod reaches Paxity and receives HTTP 401 responses — that is a successful outbound HTTPS round-trip, not a network/DNS failure.
- **MongoDB binding:** No. Temp orders (`order=tmp_...`) are created before the Paxity call; no Mongo errors in logs. Writes are working.
- **Ingress / proxy body or response-size limit:** No. The request never reaches the QR/response-building stage; it fails at the Paxity 401 upstream call first. The 502 happens in ~1.1s, well before any size handling.
- **Missing dependency (qrcode / pillow) in the prod image:** No. No ImportError/traceback for PIL/qrcode; the failure is the 401 upstream, which happens before QR generation.
- **Tier / resources:** Not implicated. tier_1 (Launch): cpu 250m/500m, mem 1Gi/2Gi, 2 replicas — no resource pressure observed.

## Root cause
Production secret `PAXITY_V2_API_KEY` holds a stale / revoked key. Paxity returns 401 for every transaction create, and the payin route surfaces that as a 502. Preview works because the preview pod has the valid new key in its `.env`; that value was never propagated to the production Secrets store.

## Fix (user action — then redeploy)
1. Deployment Panel → **Secrets**: set `PAXITY_V2_API_KEY` to the new key `pax_live_OsYI4r5imHfMAQ8oZ6YpP6XoBdnGXY2A` (remove/overwrite the old `pax_live_iGCV57WFaQbBuSgOi5Rh4TEr8hob2UJa`).
2. **Redeploy** so the new secret value is written into the production run's environment.
3. Verify: `POST /api/paxity/payin` on https://shoppingenchine.com should return 200 with a `pay.wave.com/...` link.

### Optional code hardening (E1 / main agent)
When Paxity returns 401 (or any non-2xx), return a clean 4xx/502 JSON error from `create_payin` instead of a bare 502, so the frontend can show a meaningful message and the failure is easier to diagnose.
